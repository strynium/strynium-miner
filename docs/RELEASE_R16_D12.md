# 服务端 R16 / 本地加密端 D12 · 2026-10-31

R16 修复 BTC 矿机显式请求版本滚动时被默认配置拒绝的问题，改为与该矿机的独立上游按真实能力协商。依据包括 S19 XP Hydro / Uniplus 的实际握手与同一出口的鱼池响应。保留掩码交集、请求与提交格式、nonce、任务及账户隔离；未请求该能力的矿机沿用原流程，明确不支持时不伪造支持。此补丁不增加 BCH/LTC 的版本滚动能力。

抽水运行时修复严格 30 秒格点与进程恢复相位。历史 checkpoint 可恢复，不清账本、不改费率；每批最多推进 64 个 tick，批间释放锁。普通份额只推进本矿机，抽水在入账前完成推进，入账后不增加取消点。尚未推进完成的估计器暂不参加抽水候选。

组合回归：**1197 通过、0 失败、9 忽略**，范围为 fee-module、proxy-core、minerproxy-server 的 release 库与集成测试。之后仅将一处保留原错误的 map_err 改为等价的 inspect_err，以满足零警告要求；最终源码的服务端全库测试 **268 通过、0 失败、9 忽略**，三 crate 全目标 Clippy（-D warnings）通过。两组数量有重叠，不相加。独立审查确认最后修改不改变副作用、错误传播或锁边界；未发现阻断问题。

Windows x64 与 Linux x64 musl 使用批准的构建入口完成构建；R16 服务端的隔离 HTTPS 控制台、证书和健康接口启动通过。D12 三个平台包直接复用上次发布的原文件，无须重复更新本地端。编译入口构建整个 workspace，但本次仅收集服务端新二进制。

性能诊断使用 1024 个估计器、模拟 6 小时停顿：单矿机份额准备约 5.6ms，后台分 11509 批推进，总计算约 6.8 秒，最长批约 3.15ms。模拟单矿机 31 天停顿时约 886ms，总计 1395 批。它们是开发机测量，不能当作矿场时延保证；长时间停顿仍会延迟该矿机第一份工作的准备，但不会整段持有全局锁。

更新命令：
```bash
bash <(curl -fsSL https://github.com/strynium/strynium-miner/raw/main/install.sh)
```
选择 **1 服务端 → 1 安装 / 更新**。管理器先备份再切换，保留账号、端口、证书、授权和数据；运行中的服务短暂重启，健康失败回退。管理器本身仍为 1.0.3。

**现场验收尚未完成。** 当前结论是已修复并验证软件缺陷，不是已经恢复该矿机的 280–300 TH/s。更新后先接一台，连续观察至少 30 分钟：矿机本机算力、有效/拒绝份额、错误增长、断线重连及运行时长；对比同一时段。没有执行的长时间/人工用例不计为通过。
